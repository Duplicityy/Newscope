## Working iDungeon and other automation

The selected runtime is authoritative. Corresponding [recovery source](D:/Newscape-IDungeon/20261117-recovery-01/build/compile02/source/io/ruin/model/activities/dungeoneering/IDungeon.java) organizes a single owner session per Player as a tick-driven Run with settings snapshot, explicit state, watchdog, and native IDungeonActions. Runtime bytecode confirms the later walk-only manual stop. Older source alone shows the prior generic manual-input behavior. [Walk-only hotfix receipt](D:/Newscape-IDungeon/20261117-walk-only-hotfix/RECEIPT.json)

- Floor selection considers unlocked floors, completion and settings. The planners navigate the native room graph, handle live doors, interpret puzzles and boss mechanics, and use ordinary actions through the current encounter. IDungeonCombatPlanner, IDungeonBossPlanner, IDungeonPuzzlePlanner, IDungeonPath and IDungeonPrayer separate domain decisions.
- The action layer calls native movement, object, NPC, pickup and item-on-object paths. It verifies resident objects and actors, encounters, equipment and inventory. The client handles presentation while the server worker owns action scheduling.
- IDungeonWatchdog tracks meaningful outcomes such as room, puzzle or floor progress. Recovery refreshes the target, tries an alternate approach or normal group gatestone, then verifies native exit, reward/escrow save and old party/map cleanup. Restart counts and delays are bounded. Changed floor identity or unfixed save issues prevent a restart. Respawn clears old observations and lets the controller pick up from explored rooms.
- The owner-gated IDungeonInterface provides settings, pause, resume, stop and leave. Logout removes transient run and menu state. Preserve its existing flow. [Pure checks](D:/Newscape-IDungeon/20261117-recovery-01/checks/pure01/RESULT.json) · [Controller fixture](D:/Newscape-IDungeon/20261117-recovery-01/checks/fixture01/RESULT.json)
- RaidAuto, ToaRaidAuto and TheatreRaidAuto also exist. They detect existing raid contexts and use legitimate actions. Keep them operating alongside any new planner without overlapping control.
- The separate Adventurer system has a planner and 12 named skill paths in KronosActivityPort. FishingCookingActivities, TrainingSites and ProtectionPrayerPolicy illustrate inventory-aware plans, bounded local catalogues, consumable checks, recovery and route telemetry. The adapter requires an Adventurer and its actor-specific profile, safety and quarantine. Reuse vetted game actions and planning patterns for the owner. [KronosActivityPort.java](D:/Newscape-Map-Walk/source/Kronos-master/kronos-server/src/main/java/io/ruin/model/entity/player/autonomous/KronosActivityPort.java)
- The previously adapted iDungeon logic predates this work. See the repository research for the public RareBot-era source and copying suitability. The private working implementation is the relevant reference for server control.

## Bosses and client controls

**Zulrah** has authored forms, rotations, movement, attack timing and snakelings. **Vorkath** has ordinary attacks and acid/freeze specials. **Phantom Muspah** has a 242 instance/asset gate, a shield, clouds and spikes. **God Wars Dungeon** includes native access requirements and bosses. **Chambers of Xeric** has native layout generation and encounter logic, while owner automation is unverified. **Theatre of Blood** and **Tombs of Amascut** already have dedicated owner controllers. Cache and client material for Gauntlet, Nex or Araxxor does not establish a playable server port. [Boss placement sources](D:/Newscape-Map-Walk/source/docs/world/BOSSES_AND_QUESTS.md)

The v37 owner Android client uses a native host with an embedded game bridge and retained foreground session. The manifest explicitly locks MainActivity to sensor landscape. A compact game-authenticated native options panel can reuse the iDungeon menu and protocol. Portrait controls require a tested client host change. A browser dashboard would add a separate trust boundary and hosting service. Keep each selected action server-authorized and on the world worker. [Android manifest](D:/Newscape-Map-Confirm/android/kronos/src/main/AndroidManifest.xml:11)

## Local selection priorities

1. Mining offers a tractable first vertical slice. Levels, tools, rock identity, depletion, approaching and inventory capacity have authoritative APIs. Use native outcomes and the verified 242 aliases where installed.
2. Woodcutting and Fishing → Cooking can reuse resource handling and bank checks. The actor system illustrates bounded catalogues for these. Firemaking or Fletching can consume logs acquired through those normal actions.
3. Slayer needs a first-task allowlist, exact requirements and encounter-aware safety. Later bosses should plug into shared supply and defence policy with encounter-specific timings.
4. Keep working iDungeon and raid controls. Mark unsupported encounters and methods unavailable until each has new runtime evidence.
