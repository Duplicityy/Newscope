# Private raid drop-in tooling

The builder and installer are separate. The builder can create a non-installable draft before runtime checks finish. A final pack requires completed, byte-bound private verification. The installer is supplied for a future explicit owner action; it has not been run as part of writing/reviewing these tools.

## Build

`tools/content242/Build-RaidDropInPack.ps1` accepts Workspace, Candidate, AssetCandidate and a new Output directory. `-Draft` emits only PROPOSED-PACK.json with DRAFT_NOT_INSTALLABLE status. No activation, classes or cache are copied in that mode.

For a final pack, also provide `-Verification <attestation.json>`. The format is in `tools/content242/schemas/raid-drop-in-verification.schema.json`:

```json
{
  "schemaVersion": 1,
  "status": "PASS",
  "candidate": "<exact final private runtime path>",
  "candidateManifestSha256": "<SHA256 of its CANDIDATE.json>",
  "raidDataSha256": "<SHA256 of its data/raids/near-reality-raid-assets.json>",
  "checks": [
    {"kind":"initialized-preflight","status":"PASS","path":"<final map preflight JSON>","sha256":"<its SHA256>"},
    {"kind":"ToB-smoke","status":"PASS","path":"<reviewed ToB smoke JSON>","sha256":"<its SHA256>"},
    {"kind":"ToA-smoke","status":"PASS","path":"<reviewed ToA smoke JSON>","sha256":"<its SHA256>"},
    {"kind":"asset-decoders","status":"PASS","path":"<ASSET-VERIFICATION.json>","sha256":"<its SHA256>"}
  ]
}
```

All underlying JSON receipts must actually have status PASS. The final initialized preflight must belong to the exact candidate/data, report ToB/ToA ready, and pass all twelve temporary map-copy checks. Each ToB/ToA/compendium summary independently requires `candidate`, `candidateManifestSha256`, `raidDataSha256`, and a nonempty `sourceReceipts` array of `{path,sha256}` referencing its actual native evidence. A top-level attestation cannot turn an old candidate's smoke into verification of new class bytes. Rerun the checks when candidate classes change. Packaging checks every referenced receipt hash but distributes only sanitized check/hash summaries.

The ToB smoke requires normal login, Bosses entry, populated Maiden room, native walking, actual incoming damage, normal exit, native logout and observed LOGIN_SCREEN. The ToA smoke requires normal login, a populated puzzle, actual waterfall fill and palm delivery, normal exit, native logout and observed LOGIN_SCREEN. Both require the exact fingerprint evidence described below. These bounded checks establish only their named scope; full boss kills, full clears, reward claims, multiplayer and physical Android testing remain separately documented and must never be inferred.

`raid-native-smoke.schema.json` documents the progression-aware native evidence. Required true fields are `exactPreExitInventoryEquipmentAttributeFingerprintsPreserved`, `originalFixtureAttributesPreserved`, `sixSystemProgressionPreserved` and `normalReloginInventoryEquipmentAttributeFingerprintsPreserved`, with a nonempty `fingerprintScope`. The pre-exit snapshot must be taken on the same real World executor immediately before the normal raid-leave menu action, excluding only actual temporary loans; the after-exit fingerprint includes all permanent inventory/equipment slots, amounts and attributes, including every current six-system key. Original fixture items and attributes are checked separately: legitimate combat may change the four established equipment progression keys `six.instance`, `six.condition`, `six.wear` and `six.wearTick`. That stable-fixture check does not discard those keys from the exact exit or normal logout/relogin checks. Normal logout and actual native relogin must preserve the latest full postcombat snapshot, including all six-system progression. Record the actual bracket, loan exclusions, permitted progression keys and relogin snapshot in `fingerprintScope`. The former blanket `exactInventoryEquipmentAttributeFingerprintsPreserved` flag is not accepted as an alias for these separate checks.

The earlier V5 comparison against a precombat equipment fingerprint legitimately failed when enabled six-system armour progression added or changed its own attributes. Keep that failed evidence as recorded. A later V6 success proves its own actual timed exit/relogin brackets and stable original attributes; it does not retroactively turn the old comparison into a pass or disable six-system progression.

When the candidate contains the Loot Compendium, all three server class families and CommandHandler/NPCActionHandler hooks must be present. Final packaging additionally requires `-ClientArtifacts <CLIENT-OVERLAY-MANIFEST.json>` and one `loot-compendium` attestation check. ## Future owner installation

Extract the pack into a directory and run its exact installer while all game/cache JVMs are normally stopped. Supply the existing Workspace and a **new, separate destination whose parent already exists**, for example a fresh directory under D:/Newscape-Raids-Work. The default only stages files. Add `-StartLoopback` to stage and launch privately in one command; it cannot silently start publicly.

The installer validates all pack hashes, the actual selected native bundle, all game/update libraries, the complete known-good Dungeoneering payload, six-system selection and classes, and every endgame/home/chat overlay. It rejects changed base files, ports13302/7304 in use, a still-running game/cache JVM, duplicate destinations, path traversal and reparse points. It never stops a service, removes a release or changes Start-Kronos, Start-Dungeoneering, selected public state, account files or save folders.

The new destination gets its own classes/cache and a local copy of the existing static data with only data/raids merged from the pack. Its workdir properties are generated **locally from the original file**, changing only cache_path/data_path; no credentials/configuration are distributed. Existing account/player-data/home/six-system/adventurer locations remain the same. All pre-existing enabled flags and registration behavior come from the SHA-pinned native launcher.

The derived launcher retains `$dg` as the original known-good release for original checks and classpath. The effective game order is new raid/compendium classes, old Dungeoneering, six systems, endgame armour, home, chat, sealed native libraries. Working directory/cache/data, PIDs and stdout/stderr go to the new release; immutable old release logs are not overwritten. Updater classes remain the original known-good overlay. An install marker distinguishes the actual new processes from old releases. The default remains private. `-Public` requires the separately completed, exact-install `PUBLIC-READINESS.json`; the installer never creates that authorization marker.

The private launcher defaults to the successful3584MiB game/256MiB updater,128MiB initial heaps and ParallelGC/GCTimeRatio9/MinHeapFreeRatio10/MaxHeapFreeRatio20. It requires baseline physical RAM below60%, preserves the original capacity check and starts the exact current Watch-RaidPrivateMemory.py before any JVM. The guard records owned PID/executable/creation identity, requests guarded normal saves/logout at82% and closes only those private JVMs at83.5%, before the85% ceiling. It uses packaged guarded stop helpers and a locally generated private CANDIDATE identity. The existing production state locations are preserved. It refuses to launch beside an existing game/cache process and never launches a desktop client automatically.

Do not create a READY marker while any check is pending.

Physical Android gameplay and any remaining source-versus-official differences must stay explicit.

StopRaidReleaseGame refuses private/base/other JVMs and requires the matching public bind, install property, workdir and readiness identity before using the native save/logout path. Its source and a separately compiled small helper jar are reviewable; preparing them does not start or authorize a public service.

Final pack construction also requires `public-release-tools/FROZEN-PUBLIC-TOOLS.json` and its hashed static-check receipt. They bind the compiled helper to its exact Java source, the separate public watcher and the reviewed readiness validator. The checks use in-memory synthetic proofs to verify rejection of missing bot/GUI completion, other candidate bytes, bounded raid smoke, absent relogin, other paired clients and the old protocol. They create no public-readiness file and do not claim an actual public launch or shutdown test.

Public mode continues to reference the existing **real** workspace accounts, player-data, home, six-system and adventurer paths from the pinned launcher. Private copied saves/accounts/test state are never promoted. Publication uses only the explicit sanitized source/artifact whitelist; no Git history, player state, credentials, local readiness proofs with private paths or entire smoke directories are uploaded.

All old releases and backups remain available. Rollback requires normal shutdown and explicitly choosing the previous launcher; neither tool kills processes or performs an automatic destructive rollback. A partially failed install leaves only the new incomplete directory and does not change activation pointers.
